## Objective
Measure whether independent agents (Antigravity, Claude Code, Codex, etc.) reach the same correct conclusion when applying the Responsive Engineer methodology to unfamiliar, real-world repositories. The most important metric is **agreement on classification and outcome**, rather than raw scoring.

## Evaluation Metrics
For every trial across agents, we will track:
- **Diagnosis Agreement**: Did the agents identify the same root cause?
- **Repair Agreement**: Did the agents apply structurally equivalent repairs?
- **Classification Agreement**: Did they agree on the Failure Classification (e.g., `STRUCTURAL_BUG` vs `INTENTIONAL_BEHAVIOR`)?
- **False-Positive Rate**: How often did an agent invent a bug or unnecessarily transform a component that was actually fine?
- **False-Negative Rate**: How often did an agent miss an observable responsive failure?
- **Regression Rate**: Did fixes cause desktop or cross-component regressions?
- **Accessibility Compliance**: Did interaction transformations maintain required ARIA and touch-target standards?

## Failure Analysis Methodology
When an agent fails to achieve a perfect 100 on the real-world scoring matrix, the failure must be triaged into one of the following root categories:
1. **METHODOLOGY FAILURE**: The Responsive Engineer `SKILL.md` was insufficient.
2. **EXECUTION FAILURE**: The agent misunderstood or ignored the methodology.
3. **TOOLING FAILURE**: The environment lacked browser automation or file visibility.
4. **OBSERVABILITY FAILURE**: The application could not be rendered (API/DB blocked).
5. **HUMAN-JUDGMENT FAILURE**: The issue requires product/design consensus that cannot be rigidly automated.
